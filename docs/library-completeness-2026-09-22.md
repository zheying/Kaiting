# 曲库完整浏览与播放

交付日期：2026-09-22。

本轮解决首页仅加载 60 首、收藏和专辑/艺人最多 200 项、搜索先截断再过滤，以及“播放全部”实际只播放已加载歌曲的问题。未改动真实音乐或原运行数据库。

## 已交付

- 歌曲、收藏、专辑、艺人列表显示筛选后的总数，并提供上一页/下一页。歌曲与收藏每页 60 首，专辑 24 张，艺人 30 位。
- 搜索覆盖整个曲库；歌曲、专辑、艺人各自分页，互不改变其他类别的页码。专辑和艺人使用普通子串匹配，中文、Unicode 大小写、`%`、`_`、斜杠按字面内容处理。
- 搜索关键词保存在 `#/search/:q`。详情返回恢复查询及当前分页；页面刷新恢复查询，分页从第一页开始。
- “播放全部”分别针对整个曲库、所有收藏、所有匹配歌曲。先加载完整列表，显示数量后点击“开始播放”；准备可取消、失败可重试，准备期间不替换正在播放的队列。
- 完整队列每次最多请求 500 首，并核对跨页版本、总数和唯一歌曲 ID。途中内容变化或请求失败时拒绝交付部分队列。
- 待播清单每页显示 50 首，实际播放顺序仍使用完整队列。单曲列表点击从选中歌曲开始播放当前页，页面已说明其范围。
- 收藏变化同步列表、搜索、详情、当前歌曲与队列；末页删空时回退，并同步内部页码，后续新增收藏不会跳回旧末页。失败显示中文反馈。
- 扫描完成时刷新当前分页、搜索和详情，并作废未开始播放的旧准备列表。
- 歌曲响应带 `albumKey`，播放器打开专辑不依赖当前显示的专辑页；旧播放记录缺少该字段时通过单曲接口补取。
- 大队列存储失败时不中断播放，并清除陈旧快照；普通进度保存最多每秒一次。浏览器存储容量不足时不能保证刷新后恢复整条队列。

## 接口合同

`GET /api/tracks`、`GET /api/albums`、`GET /api/artists` 新增 `page=true` 返回：

```ts
{
  items: T[];
  total: number;
  limit: number;
  offset: number;
  revision: string;
}
```

三类列表支持 `q/limit/offset`，歌曲另支持 `favorite`；`limit` 最大 500。省略 `page` 或传 `false` 保留旧数组响应。歌曲默认 80 条、专辑和艺人默认 200 条，但可通过分页访问所有数据。

数据与 `revision` 在同一 SQLite 读事务中取得。版本覆盖本连接写入、外部连接写入和服务重启，避免在总数未变化时混入不同版本的曲库。为保证一致性，其他数据库写入也可能使准备过程失效，此时可重试。

`/api/search` 继续提供 25/12/12 条预览，查询范围已修复为全库；当前搜索页面使用三个分页列表接口。专辑和艺人详情取消原先查找前 10,000 项的限制。

## 验证证据

自动测试：

- 243 首歌曲/专辑/艺人、223 首收藏逐页遍历，排序稳定且无重漏；末页、空页、过滤后总数、非法参数和旧数组响应均覆盖。
- 超过 10,000 个分组的专辑/艺人详情可访问，包含 SQLite 大小写规则一致的专辑链接。
- 完整收集 1,054 首歌曲；途中失败、取消、空页、重复、总数变化，以及增删抵消导致总数不变的版本变化均有回归。
- 外部连接在旧读事务期间提交后，旧页数据与版本仍一致；下一次读取取得新版本。
- `npm test`：13 个测试文件、203 项通过。
- `npm run typecheck`、`npm run build`、`git diff --check`：通过。
