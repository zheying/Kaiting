# 专辑自动补全的字段共识验收

目标：扫描后无人干预地补齐可信年份、流派；同一音乐内容的多个发行版本不再自动等于“全部不能补”。人工编辑、目录隔离和源音乐只读约束不变。

## 实现前确定的失败方式与预期

| 场景 | 预期 |
| --- | --- |
| 多个正式版本的年份、流派相同 | 两项自动保存，保留各字段对应的发行来源 |
| 年份冲突、流派一致；或流派冲突、年份一致 | 只保存有共识的字段，不投票猜测另一项 |
| 有些版本没有年份或流派 | 缺值不等于冲突；只采用其他已确认版本明确提供且一致的值 |
| 艺人是合辑通用署名，或数字版与实体版碟数不同 | 必须额外核对完整曲目名称及逐曲时长，才能放行；具体艺人冲突仍拒绝 |
| 同名同曲目数但歌曲不同、少曲/附赠版、时长明显不同 | 不自动保存；曲目名称比较保留版本字样、数字及重复项数量 |
| 多于原来的五个候选 | 在有限的查询预算内核对完整结果；超过预算或结果截断继续跳过 |
| 非正式版本、详情失败、详情身份改变、缺少必要曲目证据 | 不降低可靠性要求，不从失败的查询得出共识 |
| 发行曲名是英文、同一 recording 的规范曲名是日文；或有发行方统一前后缀 | 可使用提供方明确关联的两种曲名；保留上游版本后缀。本地统一前缀仅在能由专辑名称解释时忽略，不能任意剥离 Live、Remastered 等版本词 |
| 原始标签或人工设置已有值、后台结果晚到、目录/曲目变化 | 不覆盖；完整曲目证据变化必须使缓存失效 |
| 本轮只补了一项，后续补另一项 | 保留原有自动值及其来源，不把两次查询混成一个虚假的来源 |
| 服务重启、备份恢复、旧数据库升级 | 已有来源、人工管理标记、收藏和歌单保持可用 |

验证采用独立临时曲库：先通过查找服务、后台队列和真实 SQLite 的定向集成测试复现失败，再用生产构建 E2E 验证扫描、页面刷新、编辑与来源。E2E 保存截图、trace、请求记录、音乐哈希和数据库检查。生产只进行部署验收，不用真实曲库注入测试故障。

接口依据：[MusicBrainz API](https://musicbrainz.org/doc/MusicBrainz_API) 的 release 查询、recordings/artist-credits 扩展及限速要求。只发专辑名和发行 ID，本地曲目证据在服务内比较。
